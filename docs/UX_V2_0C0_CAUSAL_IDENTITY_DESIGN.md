# UX2.0C0 — Minimum Authoritative Causal Contract

Status: design/audit only. This document proposes the smallest engine and
orchestrator contract needed for UX V2. It does not implement the contract,
change gameplay rules, change React/CSS, add final runtime IDs, or modify the
UX V2 design source of truth.

Branch: `ux-v2`

## 1. Decision summary

The minimum contract is a server-owned causal envelope around the existing
Pending/Continuation state. It is additive and descriptive:

```text
Interaction
  interactionId
  originRef?                 // only for a later Interaction
  root frame
    frameId
    immutable origin
    mutable current state
    parentFrameId?
    stage
    checkpoint
      checkpointId
      presentationRevision
```

The envelope is created and advanced by the engine/orchestrator, persisted
with the interrupted effect, and projected identically to every viewer except
for existing private `CurrentAction` capability data. React does not create,
advance, or infer any of these identities.

The proposal deliberately leaves `resolutionId` unchanged as legacy/reference
metadata. It also leaves timeline `event.id` as a persisted public-event
reference and `actionRevision` as command freshness authority.

Two engine facts remain prerequisites for implementation rather than reasons
to invent projector heuristics:

1. Group execution must expose its actual semantic order/simultaneity.
2. Dying must persist the public event barrier through the existing
   `CurrentAction.presentation.readyAfterEventId` projection.

## 2. Four identities

### 2.1 `interactionId`

An Interaction is the continuous player-meaningful causal lifetime of one
root effect. The engine/orchestrator creates it exactly once when an
independent root effect is accepted for resolution. It is server-generated,
opaque, and never generated by a browser or viewer.

It survives every synchronous continuation of that root, including response,
damage, Dying, rescue, Negation, counter-Negation, ordinary Group participant
progress, and child Frames. It survives persistence, reconnect, polling, and
Quick Test viewer switching because it is part of authoritative room state,
not a viewer projection.

It changes only when a previous Interaction has fully settled and a later
independent effect begins. It must not change because:

- `resolutionId` changes during Duel or Negation;
- a public `event.id` changes;
- the response actor changes;
- `actionRevision` changes;
- a checkpoint or presentation revision changes;
- a synchronous child Frame starts;
- a viewer changes perspective.

It is persisted while unresolved and public in the PresentationSnapshot. It is
not secret and carries no legality authority. A nested child resolution keeps
the Interaction unless it is a later activation after the parent Interaction
has settled.

The lifecycle is:

```text
root accepted
  -> same interaction through all synchronous Frames/checkpoints
  -> root and descendants settled, no blocking work
  -> interaction ends
later delayed/persistent activation
  -> new interactionId + originRef
```

Thus `Attack -> Dodge -> Damage -> Dying -> Peach -> survive` is one
Interaction; all Duel exchanges are one Interaction; and original effect plus
Negation/counter-Negation is one Interaction.

### 2.2 `frameId`

A Frame is one independently resolving effect instance inside an Interaction.
The orchestrator creates a Frame when it starts an effect with its own effect
context and settlement/resume lifecycle. The Frame is persisted whenever that
effect can be interrupted or resumed.

The same Frame is retained when a response satisfies, modifies, cancels,
redirects, or continues the active effect:

- Attack and its Dodge response;
- every alternating Duel Attack requirement;
- Negation and counter-Negation of the current effect, unless a concrete
  engine effect instance is opened;
- ordinary AOE participant responses;
- Judgement replacement/modification;
- Peach/First Aid as the current Dying decision.

A child Frame is created when a trigger or forced effect independently runs
normal effect semantics. Examples are a Borrowed Sword forced Attack, nested
damage launched by a trigger, or a child effect launched during one Group
participant. The child has `parentFrameId` pointing to the synchronous parent
Frame and remains in the same `interactionId`.

Damage and Dying are not split merely because the implementation calls a
different function. The minimum rule is semantic: damage remains the active
Frame's `DAMAGE` stage; Dying/rescue remains that Frame's `DYING` stage unless
the engine opens an independently resolving Dying effect with its own
settlement lifecycle. The proven direct damage-to-Dying path should therefore
use one Frame. A new child Frame is reserved for an independently resolving
trigger/effect during Dying.

Frame identity is public, persisted while active, preserved on reconnect and
viewer switching, and never used for command freshness. A Frame may end while
its parent remains active; the parent resumes once, using explicit typed
continuation data.

### 2.3 `checkpointId`

A Checkpoint is a stable, player-facing semantic boundary inside the active
Frame. The authoritative orchestrator creates the next checkpoint when the
public meaning of the active decision/effect reaches a new stable boundary:

- the Duel responder changes;
- the Negation response actor/window changes;
- a Dying rescuer changes;
- an AOE participant advances from A to B;
- a child Frame becomes active or returns to its parent;
- a meaningful settlement or defeat boundary is reached.

It does not change for a pure HP/status update that is already part of the
same settlement boundary, an internal capability scan, a viewer switch, or a
local animation step. If a public result must be presented before the next
decision, that result may itself be a checkpoint even when no new action is
available.

Checkpoint ownership is server-side and persisted with the active causal
envelope. It is public and deterministic for all viewers. It must not be
derived from `actionRevision`, timeline position, array index, card name, or a
client timer. Its opaque value may be generated by the server, but its lifetime
is determined by the semantic transition, not by random UI state.

Reconnect, Quick Test viewer switching, and nested child resolution preserve
the current checkpoint until the authoritative engine crosses one of these
boundaries.

### 2.4 `presentationRevision`

`presentationRevision` is a server-owned public revision of the projected
PresentationSnapshot. It changes whenever the public snapshot materially
changes, including a changed root/active Frame reference, stage, public
participants/outcomes, checkpoint, settlement, transition-event set, or
public barrier reference. It may change within one checkpoint when a new
public transition/event or outcome must be rendered.

It does not change for private option differences between viewers, local
selection, animation progress, polling, reconnect, or a stale command that
does not mutate authoritative public state. It is not a gameplay revision and
must never be accepted by a command endpoint in place of `actionRevision`.

The revision is persisted or reproducibly recovered from persisted public
causal state so reconnect cannot manufacture a new scene revision. It is
public; all viewers of the same room state receive the same value. Viewer
switching changes only the private `CurrentAction` projection.

The distinction is intentional:

```text
interactionId        causal lifetime
frameId              active independent effect lifetime
checkpointId         stable semantic boundary
presentationRevision public snapshot change
actionRevision       stale-command authority
```

## 3. Immutable origin and mutable current state

Every Frame that can be redirected or otherwise mutate its active target must
carry two separate records. Origin is written once at Frame creation:

```text
origin:
  originSourceId
  originEffect
  originalTargetIds[]
  originRef?            // only when this Frame is linked to a later Interaction
```

Current state is updated by authoritative effect transitions:

```text
current:
  currentSourceId
  currentEffect
  currentTargetIds[]
  resolvingPlayerId?
```

A redirect from B to D is therefore represented as `originalTargetIds: [B]`
and `currentTargetIds: [D]`; the origin is never reconstructed from current
state. Origin is public presentation context only. Current target legality
continues to use the existing authoritative rules and `CurrentAction`.

## 4. Parent, cause, and historical origin links

These are three different relationships and must not share one field.

| Link | Meaning | Lifetime | Example |
| --- | --- | --- | --- |
| `parentFrameId` | synchronous nesting relationship | while child/parent causal work is unresolved | nested damage during a Group participant |
| `causeNodeId` | public semantic occurrence that caused a child or transition | stable public Reaction/Transition history | damage trigger caused by a damage occurrence |
| `originRef` | historical link from a new later Interaction | survives as historical provenance, not active nesting | delayed Lightning activating next turn |

`causeNodeId` is not `event.id`: one semantic occurrence may reference one or
more timeline events, and an event is a public log record rather than a causal
node. `originRef` is not `parentFrameId`: a delayed future activation must not
reopen a settled Interaction. None of these links is `actionRevision`.

## 5. Minimal Stage vocabulary

Stage is semantic presentation metadata, not identity. The engine/orchestrator
assigns it from typed effect and continuation semantics; the projector never
infers it from card names, formatted log text, seat order, or an implementation
call stack.

The proposed minimum is:

| Stage | Authoritative evidence |
| --- | --- |
| `ATTACK_RESPONSE` | typed Attack/Influencing/Borrowed-Sword Attack response continuation and Dodge/Attack requirement |
| `DUEL_EXCHANGE` | typed Duel continuation and its current alternating Attack requirement |
| `GROUP_RESOLUTION` | typed `GroupContinuation`, including active participant and explicit group semantics |
| `DAMAGE` | authoritative sourced-damage transition/`damage_suffered` continuation |
| `DYING` | typed `DyingPending` and canonical rescue continuation |
| `JUDGEMENT` | typed Judgement continuation/revealed/effective event |
| `NEGATION` | typed Negation continuation and counter window |
| `FORCED_ACTION` | typed Borrowed Sword selection/forced-effect boundary before its child Attack |
| `SETTLEMENT` | authoritative completion/defeat/return boundary with public settlement data |

`RESPONSE` and `TRIGGER` are engine pending kinds, not automatically useful
Stages. Their Stage comes from the typed continuation/event they are resolving.
If an effect cannot provide typed evidence, the projector must use a neutral
known stage or omit the stage; it must not guess from a card name.

## 6. Group semantics

UX2.0B proved Group detection for a typed Group continuation but did not prove
ordering semantics. The engine, not the projector, must own this minimum
metadata on the authoritative Group effect:

```text
group:
  resolutionSemantics: SEQUENTIAL | ORDERED | GROUP
  orderedParticipantIds[]?   // required for SEQUENTIAL/ORDERED when order matters
  currentParticipantId?
  remainingParticipantIds[]
```

`orderedParticipantIds` is the effect's declared execution order and survives
independently of seat topology. `currentParticipantId` is the participant
whose semantic boundary is active. `remainingParticipantIds` is authoritative
remaining work, not a projector reconstruction from a source array.

- `SEQUENTIAL`: one participant is resolved at a time in explicit order.
- `ORDERED`: the effect has an explicit order that is meaningful even if its
  presentation or response mechanics differ from ordinary sequential work.
- `GROUP`: participants are one semantic group and no player-facing order may
  be invented unless the engine also supplies one.

For the current AOE paths, the existing `remainingIds` queue is evidence of
execution progress but is not by itself enough to certify the public semantic
enum. C3 must populate the explicit fields at Group creation and update them
at each authoritative participant transition. Projector code must not derive
them from array iteration, seat sorting, card name, or timeline order.

## 7. Dying presentation barrier

Reuse the existing `CurrentAction.presentation.readyAfterEventId` contract.
Do not add a second Dying-only client field or alter the proven explicit rescue
timer-arm behavior.

When the engine creates `DyingPending` from lethal damage, it must retain the
generic pending presentation-boundary metadata needed for the existing route
projection to emit:

```text
CurrentAction.presentation.readyAfterEventId = <essential public event id>
```

The event is the persisted essential public damage/entered-Dying event that
explains why rescue controls are opening. It is a timeline `event.id` used as
a barrier reference only, never as `interactionId`, `frameId`, or
`checkpointId`. It is assigned after the event is emitted and before the Dying
pending state is persisted.

On reconnect, the pending barrier and the event reference are recovered from
authoritative state. If the event is already marked presented locally, the
barrier is immediately open; otherwise the client waits for that event under
the existing presentation rules. If the event is no longer available in the
bounded log, C4 must make the barrier safely open/recoverable from persisted
semantic state rather than leave rescue controls permanently blocked.

The rescue deadline remains governed by the existing explicit
`start_rescue_timer` action and authoritative deadline. C4 must prove that the
barrier does not silently consume usable rescue time across reconnect, delayed
polling, reduced motion, or fast-forward. This is a fairness test, not a new
timer model.

## 8. Transition Event contract

The Game Log remains the persisted public history. A Transition Event is a
bounded semantic presentation delta derived from an authoritative occurrence;
it is not copied prose and not a replacement log.

```text
transitionEvent:
  transitionId       // stable semantic occurrence identity
  timelineEventIds[]  // references to public Game Log events, when present
  interactionId
  frameId?
  checkpointId
  causeNodeId?
  kind
  publicPayload
```

The orchestrator creates one `transitionId` when the semantic occurrence is
committed, and persists enough occurrence identity that repeated projection,
polling, reconnect, and viewer switching return the same ID. The projector
may reference existing `event.id` values, but must not create a new transition
identity during projection or use timeline position as identity.

Transition Events are causally scoped to the current Interaction/checkpoint.
Unrelated historical log entries, even if they share a legacy `resolutionId`,
are excluded. A transition can appear in stable state, Reaction Chain,
settlement, and the transition list as multiple views of one occurrence; these
views must not become separate sources of truth.

## 10. C0-to-C7 migration plan

This is a design sequence, not authorization to begin C1 in this task.

### C1 — semantic identity metadata/types

Define shared types for the causal envelope, origin/current records, typed
parent/cause/origin links, checkpoint, presentation revision, and Transition
Event. Keep fields optional at the boundary while old rooms and old pending
records are readable. Do not promote `resolutionId` or `event.id`.

### C2 — propagate Interaction/Frame through the orchestrator

Create the Interaction at independent root acceptance, create Frames at
semantic effect boundaries, persist them through every relevant Pending and
Continuation, and preserve typed resume direction. Add runtime proofs for the
scenario matrix, including redirects and Borrowed Sword.

### C3 — add Group semantics

Make the Group owner write explicit `resolutionSemantics`, declared order,
current participant, and remaining participants. Prove ordered effects do not
depend on seat topology or projector array order. Keep legality in existing
rules/capabilities.

### C4 — add Dying barrier metadata

Carry the generic presentation barrier through Dying creation and projection
using the existing `readyAfterEventId` shape. Preserve the explicit rescue
timer arm. Add reconnect, delayed-presentation, timeout, and usable-time
fairness tests.

### C5 — update the PresentationV2 projector

Consume explicit causal metadata and typed continuation direction. Remove
heuristic root/parent/Group inference as each authoritative field becomes
available. Keep private `CurrentAction` projection unchanged.

### C6 — engine-backed architecture tests

Drive the full matrix through real Worker/D1/orchestrator paths, including
Quick Test human-seat switching, multiple viewers, reconnect, stale/double
submission, redirect, Group defeat, and nested resume. Assert identical public
identity metadata across viewers and exact private-option isolation.

### C7 — expose final PresentationSnapshot

Expose the stable public snapshot and semantic Transition Events alongside the
existing protocol. Verify idempotent reconnect/polling and public settlement
references. Only after C7 should React migration be considered; this C0 does
not authorize visual UX implementation.

## 11. Unresolved questions / explicit gates

1. What exact persisted room/orchestrator location will own the causal envelope
   without duplicating every domain continuation? The answer must preserve old
   pending records and support migration/reload.
2. Which existing public event is the canonical lethal-damage/entered-Dying
   barrier in every damage path, including source-less damage and nested
   damage? C4 must name it per typed transition, not choose by latest log scan.
3. Which concrete effect families are `GROUP` rather than `SEQUENTIAL` or
   `ORDERED`? The engine/rules owner must decide; the projector cannot.
4. Does any current Dying-triggered skill have an independently resolving
   lifecycle requiring a child Frame, or can all current direct Dying flows
   remain one Frame with a `DYING` stage?
5. What is the durable semantic occurrence key for Transition Events when one
   occurrence emits multiple timeline records and the bounded log rotates?
6. Can the existing presentation barrier bookkeeping reliably distinguish an
   already-presented event after reconnect, or does C4 need a small persisted
   presentation watermark? This must not become gameplay authority.
7. What is the smallest public settlement outcome vocabulary that avoids
   deriving outcomes from formatted log text or HP-difference inference?

These questions are implementation gates. They do not authorize heuristic
projector inference or a React-side workaround.

## 12. Scope conclusion

UX2.0C0 is complete as a proposal only. No C1 implementation has started. The
contract deliberately keeps the existing gameplay protocol and rules intact,
does not add final IDs to the current room projection, and leaves the main UX
design document unchanged pending review.
